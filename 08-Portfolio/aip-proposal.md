**Date:** September 2026

---

# 1. Executive Summary

SwiftPay is a fictional fintech application experiencing a 60% user drop-off.

The purpose of this proposal is to identify potential sources of friction within the user journey and propose a trust-centered UX strategy.

The redesign focuses on three critical areas:

1. Login
2. Home dashboard
3. Transaction confirmation

The central hypothesis is that uncertainty around security, recipient identity, transaction fees, total cost and confirmation status may contribute to hesitation and abandonment.

This hypothesis requires validation through real user research and usability testing.

The proposed solution introduces trust mechanisms directly into the interface.

These include:

- Secure connection messaging
- Account protection status
- Recipient verification
- Transparent transaction fees
- Clear transaction totals
- Security indicators
- Confirmation before irreversible actions
- Clear transaction success states
- Transaction references
- Privacy and security controls

The objective is not simply to make SwiftPay visually attractive.

The objective is to make users feel:

**Informed → Confident → In Control**

while completing important financial tasks.

# 2. BUSINESS CHALLENGE

## Current Situation

SwiftPay is experiencing:

> **60% user drop-off**

This means a significant proportion of users are not completing the intended journey.

For this capstone, the exact cause of the 60% drop-off is not provided.

# 4. Friction Assessment

| Journey Stage | Potential Friction | User Concern | Business Risk |
|---|---|---|---|
| Login | Security uncertainty | Is this service safe? | Login abandonment |
| Login | Unclear errors | What went wrong? | Repeated attempts |
| Home | Important actions unclear | Where do I send money? | Task abandonment |
| Home | Security status hidden | Is my account protected? | Trust reduction |
| Transaction | Recipient unclear | Am I sending to the right person? | Transfer hesitation |
| Transaction | Fee appears late | How much will I pay? | Surprise/frustration |
| Transaction | Total unclear | How much leaves my account? | Confirmation hesitation |
| Confirmation | Weak review state | Can I still stop this? | Fear of mistakes |
| Processing | Unclear status | Did the transfer work? | Repeated actions |
| Success | Insufficient receipt information | Can I prove this transaction? | Support requests |

# 5. Assessment of the Three Core Screens

## 5.1 Login

### Potential problem

The login stage requires users to provide sensitive credentials.

If the interface does not communicate security clearly, users may experience uncertainty.

### UX opportunity

Make security visible without overwhelming the user.

### Proposed intervention

Display:

> 🔒 Secure connection

And:

> Your personal and financial information is protected.

Also provide:

- Forgot password
- Privacy
- Security
- Help

---

# 5.2 Home Dashboard

### Potential problem

A financial dashboard contains sensitive information and multiple actions.

If the interface lacks hierarchy, users may struggle to identify what they need.

### UX opportunity

Create a clear hierarchy:

1. Account status
2. Balance
3. Primary action
4. Quick actions
5. Recent transactions
6. Security/privacy controls

### Proposed intervention

Display:

> 🔒 Account protected

Make:

> Send Money

a prominent primary action.

---

# 5.3 Transaction Review

### Potential problem

Financial transactions create a high-consequence decision point.

Users need confidence about:

- recipient;
- bank;
- account;
- amount;
- fee;
- total;
- security;
- final confirmation.

### UX opportunity

Turn the transaction screen into a structured verification checkpoint.

### Proposed intervention

Display:

> ✓ Recipient verified

Then show:

**Amount**

₦50,000.00

**Transfer fee**

₦10.00

**Total**

₦50,010.00

Then:

> Please confirm that the recipient, amount and fee are correct.

This reduces ambiguity before confirmation.

# 6. INSIGHT

## I — Insight

The friction audit suggests a central UX hypothesis:

> Users are more likely to hesitate when important financial information or security signals are unclear at the moment they need to make a decision.

This leads to a key design principle:

> **Trust should be demonstrated through the interface, not communicated only through branding.**

Instead of simply telling users that SwiftPay is secure, the experience should provide visible evidence of control and transparency.

# 13. Phase 4 — Measurement

The redesign should be evaluated using measurable UX and business metrics.

## Transaction Completion Rate

Formula:

Completed Transactions ÷ Started Transactions × 100

---

## Login Completion Rate

Formula:

Successful Logins ÷ Login Attempts × 100

---

## Abandonment Rate

Formula:

Abandoned Journeys ÷ Started Journeys × 100

---

## Task Completion Time

Measure the time required for users to complete the target task.

---

## Error Rate

Measure incorrect actions such as:

- wrong navigation;
- incorrect recipient selection;
- failed confirmation;
- repeated actions caused by uncertainty.

---

## User Trust Score

After testing, ask users to rate statements such as:

> “I felt confident completing this transaction.”

Use a defined rating scale, for example 1–5.

# 21. THE CONSULTANT'S DESIGN THESIS

The central thesis of SwiftPay TrustFix is:

> **Financial UX should make important decisions easy to understand and difficult to misunderstand.**

For a transaction involving real money, users should not have to guess:

- who will receive the money;
- how much they are sending;
- how much they will be charged;
- what the final amount is;
- whether the recipient is verified;
- whether the transaction succeeded.

The interface should answer these questions before the user commits.
